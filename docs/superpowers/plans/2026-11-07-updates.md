# App and Runtime Updates Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Playalong installs and updates itself and the runtime it makes songs with from GitHub Releases, with yt-dlp kept fresh from PyPI.

**Architecture:** Two channels on GitHub Releases, polled from a rolling release `updates`: `latest.json` (Tauri updater, signed app) and `manifest.json` (runtime + model archives, sha256-checked). The playalong Python code ships in the app bundle and goes first on the runtime's import path; yt-dlp updates through the runtime's `playalong update-downloader`.

**Tech Stack:** Python 3.12 (runtime build/pack scripts), Rust/Tauri 2 (`tauri-plugin-updater` 2.x, `tauri-plugin-process` 2.x, reqwest, zstd, tar, sha2), Svelte 5 UI, `gh` for publishing.

**Spec:** `docs/superpowers/specs/2026-11-07-updates-design.md`

## Global Constraints

- Apple Silicon only; no Apple Developer ID: README explains the one-time right-click > Open.
- Repo `spilikin/playalong`; rolling release tag `updates`; runtime releases `runtime-<YYYY.MM.DD>`; model release `model-<slug>`; app releases `app-v<version>`. None of them takes GitHub's "Latest" badge except `app-v*`.
- Runtime series: integer, starts at `1`, in `runtime.json`, the manifest and the app (`RUNTIME_SERIES`).
- Install root: `~/Library/Application Support/dev.playalong/`, runtime at `runtime/` under it.
- Downloader update: at most once per 24 h before a YouTube download, and once after a failed download.
- The updater signing key lives at `~/.tauri/playalong.key`, never in the repo; only the public key goes in `tauri.conf.json`.
- Nothing is pushed, published, or key-generated without the user's explicit go (Task 6).
- The UI for setup, progress and "make a song from a link" is shown as a mockup artifact and approved before Task 5 builds it.

## Review Focus

- No network on first launch: the app must still open and play existing songs, and say the runtime can't be fetched.
- Disk full / interrupted download mid-install: the old runtime keeps working and staging leftovers are cleared next time (pinned by `a_broken_archive_leaves_the_installed_runtime_alone`; add `leftover_staging_is_cleared` in Task 3).
- Manifest series newer than the app: the app says "update Playalong" instead of installing (Task 3 test `a_newer_series_asks_for_an_app_update`).
- A song made while a runtime update is installing: `make_song` refuses while installing (Task 4 test `making_a_song_waits_for_the_install`).
- The Python code in the app bundle vs an older runtime still holding its own `playalong` package: the bundled code wins (Task 2 check runs the launcher with `PLAYALONG_CODE` and prints `playalong.__file__`).

**Interfaces:**
- Consumes: Task 3's `installed`, `plan`, `fetch_manifest`, `fetch`, `install`, `run_cli`, `finished_folder`.
- Produces (commands, camelCase in JS):
  - `runtime_status() -> {installed: Installed|null, busy: bool}`
  - `runtime_check() -> {plan: Plan, latest: string}` (network)
